# Требования: модуль ККД (контроль качества данных по целям)

## Назначение

Сервис периодически (еженедельно) проверяет качество данных по целям и ключевым
результатам (КР) в корпоративной системе целеполагания, сохраняет результат
проверки (прогон) и отдаёт его через REST API для страницы ККД.

## Границы решения

Входит:
- схема БД и миграции с откатом;
- 4 правила проверки качества;
- расчёт трёх метрик и дельты к предыдущему прогону;
- три REST-эндпоинта;
- seed-данные: 2–3 подразделения, 20–30 целей, два прогона;
- запуск одной командой `docker compose up`.

Не входит:
- фронтенд;
- аутентификация и авторизация;
- планировщик запуска прогонов (предполагается внешний вызов);
- интеграция с внешними системами.

## Функциональные требования

### FR-1. Справочник правил
Четыре правила, применяются только к активным целям и их КР:

| Код | Важность | Что проверяет | Проблема привязывается к |
|---|---|---|---|
| GOAL_NO_OWNER | critical | у активной цели не заполнен ответственный | цели |
| KR_WEIGHTS_SUM | major | сумма весов КР цели ≠ 100% | цели |
| KR_NO_TARGET | major | у КР не заполнено целевое значение | КР |
| KR_STALE_PROGRESS | minor | факт КР не обновлялся более 45 дней | КР |

### FR-2. Прогон
Прогон фиксирует дату снимка и набор найденных проблем. Первый прогон
не имеет сравнения: предыдущие значения и дельта равны null, а не 0.

### FR-3. Метрики подразделения
Для подразделения считаются минимум три метрики с учётом дочерних
подразделений и каскадирования целей. Для каждой метрики отдаются: текущее
значение, предыдущее значение, дельта и признак «лучше / хуже / без изменений».

Scope метрики: активные цели, у которых `goal.unit_id` входит в поддерево
подразделения (по `unit.parent_id`), плюс транзитивно все их активные потомки
по `goal.parent_goal_id`. Множество дедуплицируется по `goal_id`. Потомок
может принадлежать другому подразделению — это учитывается в метриках обоих
подразделений (см. design.md, раздел «Каскадирование целей в метриках»).

### FR-4. Дельта проблем
Проблема считается «той же самой» в двух прогонах, если совпадают правило
и объект (цель или КР). Отдаются счётчики: новые, сохраняющиеся, исправленные.

### FR-5. Список прогонов
Отдаётся список прогонов: статус, дата снимка, с каким прогоном сравнивается,
число найденных проблем.

### FR-6. Список проблем
Отдаётся список проблем прогона с фильтрами по подразделению, правилу и
важности и с пагинацией (limit, offset, total).

## Нефункциональные требования

- Стек: Java 17+, Spring Boot 3+, PostgreSQL 15+, Flyway, Maven.
- Конфигурация через переменные окружения, `.env.example` в репозитории.
- Контроллеры отделены от сервисного слоя и доступа к данным.
- Логика правил вынесена в отдельный компонент, не знающий про БД и HTTP.
- Миграции поддерживают накат → откат → повторный накат.
- Весь проект поднимается одной командой `docker compose up`.

## Критерии приёмки

1. `docker compose up` на чистой машине поднимает сервис, БД, применяет
   миграции и загружает seed-данные без ручных шагов.
2. `migrate → undo → migrate` проходит без ошибок на чистой БД.
3. Каждое из 4 правил срабатывает на seed-данных.
4. В seed-данных присутствуют все три категории дельты: new, persisting, resolved.
5. `/api/runs` возвращает список прогонов с числом проблем.
6. `/api/kkd/summary` возвращает минимум 3 метрики, разбивку по важности и
   дельту new/persisting/resolved; для первого прогона предыдущие значения и
   дельта равны null.
7. `/api/kkd/issues` поддерживает фильтры и пагинацию, возвращает total.
8. Неизвестный run_id или unit_id → 404; некорректные параметры → 422.
9. Формат ошибки единый: `{"error": {"code": "...", "message": "..."}}`.
10. JUnit 5: минимум 4 сценария — два правила на граничных данных, расчёт
    метрики, расчёт дельты.
11. README содержит: запуск, тесты, проверку накат/откат, архитектуру,
    статус использования AI-ассистента.
12. В репозитории присутствует исполняемый скрипт scripts/rollback.sh, который
    корректно откатывает все миграции и очищает историю Flyway, позволяя
    выполнить повторный накат без ошибок.
