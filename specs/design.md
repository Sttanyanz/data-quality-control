# Дизайн: модуль ККД

## Модель данных

### unit

Подразделения, adjacency list. `parent_id` — ссылка на родителя, NULL у корня.

### goal

Цель. `unit_id` — организационная принадлежность для агрегации метрик.
`owner_id` — персональный ответственный (NULL допустим: это ловит
GOAL_NO_OWNER).
`parent_goal_id` — каскадирование целей. `status` — ACTIVE / DONE / CANCELLED.

### key_result

Ключевой результат цели. `target_value`, `actual_value` — NUMERIC.
`weight` — NUMERIC 0..100. `fact_updated_at` — время последнего обновления
факта.

### kkd_rule

Справочник правил. `code` — стабильный машинный идентификатор (UNIQUE),
`target_type` — на что правило порождает проблемы (GOAL / KR),
`severity` — текущая важность правила.

### kkd_run

Прогон проверки. `snapshot_date`, `status`, `compared_to_run_id`.
У первого прогона `compared_to_run_id = NULL`.

### kkd_issue

Найденная проблема. Exclusive arc на две FK `goal_id` и `key_result_id`,
обе `ON DELETE RESTRICT`. `severity` — снимок важности на момент прогона.
`message` — текст проблемы для UI.

## Ключевые решения

### 1. Exclusive arc для объектов kkd_issue

`kkd_issue` ссылается на цель или КР через две nullable FK с
`CHECK (num_nonnulls(goal_id, key_result_id) = 1)`.
`ON DELETE RESTRICT` на `goal_id` и `key_result_id` для запрета удаления целей.

### 2. Снимок severity в kkd_issue

`kkd_issue.severity` хранится отдельно в строках kkd_issue, не только в правилах
kkd_rule. Причина: изменения параметров правил в kkd_rule не должно влиять на
старые прогоны.

### 3. Идентичность проблемы для дельты

«Та же самая проблема» = совпали `(rule_id, goal_id, key_result_id)`.
Сравнение через `IS NOT DISTINCT FROM` (одна из FK всегда NULL).
Защита от дублей: unique index
`(run_id, rule_id, goal_id, key_result_id) NULLS NOT DISTINCT`.

### 4. Подсчет иерархии подразделений

Для `unit_id` рекурсивно собирается поддерево обходом в памяти (все unit
загружаются одним запросом). Метрики считаются по `goal.unit_id ∈ поддерево`,
только по активным целям.

### 4а. Каскадирование целей в метриках

Скоуп метрики подразделения расширяется с учётом каскадирования целей:

1. Поддерево подразделений: `U` и все потомки по `unit.parent_id`.
2. Базовое множество: активные цели с `goal.unit_id` в поддереве.
3. Транзитивно добавляются все активные потомки этих целей по
   `goal.parent_goal_id` — обход вниз.
4. Множество дедуплицируется по `goal_id`; циклы в `parent_goal_id`
   защищены visited-set (единый `Set<Long>` служит и дедупом, и защитой от
   циклов).
5. Все три метрики, `issues_by_severity` и дельта считаются по этому скоупу.

Следствия, принятые осознанно:

- Цель, каскадированная из другого подразделения, учитывается и в метрике
  своего подразделения (по `unit_id`), и в метрике подразделения-предка (по
  каскаду). Сумма метрик дочерних подразделений может не совпадать с
  метрикой родительского.
- Некаскадированная цель не выпадает из скоупа своего подразделения: она
  входит по `unit_id`.
- Скоуп прошлого прогона вычисляется по текущему состоянию целей (`unit_id`,
  `parent_goal_id`). При переездах целей между прогонами
  возможна неточность; снимок скоупа на прогон (`kkd_run_goal`) — при
  росте требований к воспроизводимости.

### 5. Батчевая загрузка данных для правил

Правила получают предзагруженный снимок: units, goals, krs — тремя запросами,
без N+1. `Clock` инжектируется для тестируемости правил с датами.

### 6. Доступ к данным

Для всех запросов к базе данных используется `JdbcTemplate` (`spring-jdbc`). Это
даёт полный контроль над SQL и маппингом (в частности полезно для exclusive
arc в `kkd_issue`), и снимает риск `LazyInitializationException`, который мог бы
возникнуть при использовании ORM.

### 7. Ответственный

`goal.owner_id` — идентификатор сотрудника во внешней системе управления
персоналом; таблица сотрудников вне границ модуля ККД, поэтому FK не создаётся.
Ссылочная целостность обеспечивается внешней системой; для правила GOAL_NO_OWNER
достаточно проверки `owner_id IS NULL`.

### 8. Хранение compared_to_run_id

`kkd_run.compared_to_run_id` хранится явно, а не вычисляется при чтении как
«предыдущий прогон по snapshot_date». Причина: отчёт о дельте должен быть
воспроизводимым. При вычислении на лету бэкдейтный прогон или пропуск недели
менял бы `compared_to` и дельту во всех ранее сгенерированных отчётах задним
числом.

### 9. fact_updated_at IS NULL не является нарушением KR_STALE_PROGRESS

Правило KR_STALE_PROGRESS срабатывает только при заполненном fact_updated_at.
NULL означает «факт никогда не обновлялся» — это отдельный класс проблемы с
более высоким уровнем severity, и в текущем наборе из 4 правил не проверяется.

Следствие для метрики clean_kr_share: КР с `fact_updated_at IS NULL`
считается «без замечаний» по этому правилу.

### 10. Работа с часовыми поясами и датами

- `TIMESTAMPTZ` используется для всех полей, фиксирующих точный момент времени.
- `kkd_run.snapshot_date` (тип `DATE`) — это календарный день прогона. Дата
  фиксируется в UTC.
- `goal.due_date` (тип `DATE`) — календарная дата дедлайна.

### 11. Алгоритм обхода (BFS)

Обход дерева целей выполняется в ширину (BFS). Важно: обход проходит через цели
любых статусов (ACTIVE, DONE, CANCELLED), но в итоговый `Set<Long> scopeGoalIds`
добавляются только цели со статусом `ACTIVE`. Это гарантирует, что качество
данных активных подцелей проверяется, даже если их родительские цели уже
переведены в статус DONE. Для защиты от зацикливаний (если в данных есть цикл)
используется `Set<Long> visited`.

### 12. Конфигурация через переменные окружения

В корне проекта лежит шаблон `.env.example` с перечнем всех необходимых
переменных (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`,
`SERVER_PORT`). Docker, Spring и скрипты читают их из .env или из 
окружения, либо используют значения по умолчанию.

### 13. Расчет метрик и трендов в Summary

- Все значения метрик и их дельта (`delta`) округляются до 1 знака после 
  запятой, чтобы избежать артефактов вычислений с плавающей точкой.
- Для определения тренда (`trend`) используется допуск (эпсилон): если
  `Math.abs(delta) < 0.01`, тренд считается `stable` (без изменений).
- Направление тренда зависит от бизнес-смысла метрики (свойство
  `higher_is_better`). Для `avg_issues_per_goal` уменьшение значения считается
  трендом `better`.
- Расчет дельты проблем между прогонами (для получения `new`, `persisting`,
  `resolved`) выполняется с помощью SQL CTE (`WITH`) и оператора
  `IS NOT DISTINCT FROM` для корректного сравнения колонок с возможными `NULL`.

## API

### GET /api/runs

Список прогонов: `id`, `snapshot_date`, `status`, `compared_to_run_id`,
`issues_count`.

### GET /api/kkd/summary?run_id=&unit_id=

- `run` — id и дата снимка;
- `compared_to` — id и дата предыдущего прогона или null;
- `unit` — id и имя;
- `metrics` — минимум 3 метрики: `key`, `title`, `unit`, `value`, `previous`,
  `delta`, `trend` (better / worse / stable);
- `issues_by_severity` — current / previous / delta по critical, major, minor;
- `delta` — new / persisting / resolved.

Скоуп метрик — с учётом каскадирования целей (раздел 4а).

### GET /api/kkd/issues?run_id=&unit_id=&rule=&severity=&limit=&offset=

Список проблем: `items`, `limit`, `offset`, `total`. Элемент: `id`,
`rule_code`, `severity`, `target_type` (GOAL / KR), `target_id`, `message`.

Формат ответа для списка с пагинацией:
{
"items": [ ... ],
"limit": 20,
"offset": 0,
"total": 20
}

### Ошибки

Неизвестный run_id или unit_id → 404. Некорректные параметры → 422.
Формат: `{"error": {"code": "...", "message": "..."}}`.

## Инфраструктура

- Flyway: V1 схема (CREATE TYPE + таблицы + индексы), U1 откат схемы,
  V2/U2 справочник правил, V3/U3 seed. Для seed откат — `TRUNCATE` с
  `RESTART IDENTITY`.
- `docker compose up -d --build` поднимает весь стек, состоит из:
  - `postgres`: образ `postgres:15` с healthcheck и volume для данных.
  - `app`: Spring Boot приложение, собираемое через многоэтапный `Dockerfile`
    (`eclipse-temurin:21-jdk-alpine` для сборки, `jre-alpine` для запуска).
    Стартует только после успешного запуска БД
    (`depends_on: condition: service_healthy`).
- Для ручного управления миграциями Flyway используются bash-скрипты:
  - `scripts/migrate.sh` - накат
  - `scripts/rollback.sh` - откат
- Конфигурация через .env/переменные окружения, `.env.example` в репозитории.

## Тесты (JUnit 5)

Обязательные 4: два правила на граничных данных, расчёт метрики, расчёт дельты.
Дополнительно: первый прогон (null, не 0) и тест на каскадный скоуп (цель в
одном юните, каскадированная от цели другого; некаскадированная цель
не выпадает; дедупликация; цикл не вешает обход).
