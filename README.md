# Модуль контроля качества данных (ККД)

Сервис предназначен для автоматической проверки качества данных по целям и
ключевым результатам (КР), а также для предоставления статистики и динамики
(дельты) изменений для руководителей и администраторов.

## 🛠 Технологический стек

- **Java 21**
- **Spring Boot 3 (Web, JDBC)**
- **PostgreSQL 15**
- **Flyway** (управление миграциями БД)
- **Docker / Docker Compose**
- **JUnit 5 + Mockito** (тестирование)

## 🚀 Как запустить проект

Проект полностью контейнеризирован. Для запуска потребуется только установленный
Docker.

1. **Настройка окружения:**
   Скопируйте шаблон переменных окружения:
   `cp .env.example .env`
   *(При необходимости измените порты или пароли в файле `.env`)*

2. **Запуск всего стека одной командой:**
   `docker compose up -d --build`

   Эта команда соберет Docker-образ приложения, поднимет базу данных PostgreSQL,
   дождется ее готовности, автоматически накатит все миграции (схему и тестовые
   данные) и запустит само приложение.

   Приложение будет доступно по адресу: `http://localhost:8080`

## 🧪 Как запустить тесты

Для запуска тестов (юнит-тесты правил, интеграционные тесты метрик и дельты)
выполните:
`./mvnw test`
*(Убедитесь, что контейнер с базой данных запущен, так как интеграционные тесты
подключаются к реальной БД).*

## 🔄 Проверка миграций (Накат → Откат → Повторный накат)

В проекте используется Flyway Community Edition, который не поддерживает
автоматический откат. Поэтому для управления миграциями написаны bash-скрипты.

1. **Накат (Применение схемы и данных):**
   `./scripts/migrate.sh`

2. **Откат (Удаление всех таблиц и данных):**
   `./scripts/rollback.sh`

3. **Повторный накат:**
   Снова выполните `./scripts/migrate.sh`. Все миграции (V1, V2, V3) применятся
   без ошибок, что подтверждает корректность скриптов отката (U1, U2, U3).

## 🏗 Архитектура решения

Проект построен по классической слоистой архитектуре: **Controller → Service →
Repository**.

### 1. Логика правил (Rule Engine)

Согласно ТЗ, логика правил полностью изолирована от слоя API и БД.

- **Где живет:** Пакет `rule`.
- **Как работает:** Интерфейс `KkdRule` реализуется 4 классами (например,
  `GoalNoOwnerRule`, `KrWeightsSumRule`). Они принимают объекты целей/КР в
  памяти (Records) и возвращают список найденных проблем (`IssueProposal`).
  Класс `RuleEngine` просто перебирает все реализации правил.
- **Интеграция с БД:** Сервис `KkdRunService` загружает данные из БД через
  репозитории, передает их в `RuleEngine`, а затем сохраняет найденные проблемы
  в таблицу `kkd_issue`.

### 2. Расчет метрик и дельты

- **Метрики** (`clean_kr_share`, `avg_issues_per_goal`, `critical_goals_share`)
  рассчитываются в `KkdSummaryService` на основе агрегированных данных из
  `MetricsRepository`. Значения округляются до 1 знака после запятой.
- **Дельта** (new / persisting / resolved) рассчитывается на уровне SQL
  (`SummaryDeltaRepository`) с помощью CTE и оператора `IS NOT DISTINCT FROM`
  для корректного сравнения NULL-полей. Для первого прогона дельта равна `null`.
- **Каскадирование:** Скоуп метрик (список `goalIds`) собирается в
  `ScopeService` с помощью обхода в ширину (BFS) по иерархии подразделений и
  целей.

### 3. Особенности БД

- Для таблицы проблем (`kkd_issue`) используется паттерн **Exclusive Arc** (две
  колонки `goal_id` и `key_result_id` с CHECK-ограничением), чтобы избежать
  полиморфных связей.
- Поле `severity` в проблеме — это **снимок** важности на момент прогона, чтобы
  изменения в справочнике правил не искажали историю.

## 🤖 Использование AI-ассистента

Решение разрабатывалось с активным использованием AI-ассистентов (ChatGPT/Claude
для архитектурных решений и SQL, GitHub Copilot/JetBrains AI для генерации
boilerplate-кода).

Все ключевые архитектурные решения, модели данных и спецификации API
зафиксированы в папке **`specs/`** (файлы `requirements.md` и `design.md`).
Генерация кода выполнялась строго на основе этих спецификаций.

## 📌 Эндпоинты для проверки

- `GET /api/runs` — список прогонов с количеством проблем.
- `POST /api/runs` — ручной запуск нового прогона (находит проблемы и сохраняет
  в БД).
- `GET /api/kkd/issues?run_id=1&limit=10` — список проблем с пагинацией.
- `GET /api/kkd/summary?run_id=2&unit_id=1` — метрики, дельта и статистика по
  severity.
