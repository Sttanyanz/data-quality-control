# Модуль контроля качества данных (ККД)

Сервис предназначен для автоматической проверки качества данных по целям и
ключевым результатам (КР), а также для предоставления статистики и динамики
(дельты) изменений для руководителей и администраторов.

## 🛠 Технологический стек

- **Java 21**
- **Spring Boot 3 (Web, JDBC)**
- **PostgreSQL 15**
- **Flyway** (управление миграциями БД)
- **Docker / Docker Compose**
- **JUnit 5 + Mockito** (тестирование)

## 🚀 Как запустить проект

Проект полностью контейнеризирован. Для запуска потребуется только установленный
Docker.

1. **Настройка окружения:**
   Скопируйте шаблон переменных окружения:
   `cp .env.example .env`
   *(При необходимости измените порты или пароли в файле `.env`)*

2. **Запуск всего стека одной командой:**
   `docker compose up -d --build`

   Эта команда соберет Docker-образ приложения, поднимет базу данных PostgreSQL,
   дождется ее готовности, автоматически накатит все миграции (схему и тестовые
   данные) и запустит само приложение.
   
   Приложение будет доступно по адресу: `http://localhost:<SERVER_PORT>` (по
   умолчанию `http://localhost:8080`).

## 📌 Описание API (Endpoints)

Базовый URL: `http://localhost:<SERVER_PORT>` (по умолчанию
`http://localhost:8080`).

### 1. Получить список прогонов

`GET /api/runs`
Возвращает список всех прогонов с количеством найденных проблем в каждом.

**Пример ответа:**

~~~json
[
  {
    "id": 2,
    "snapshotDate": "2026-10-26",
    "comparedToRunId": 1,
    "status": "COMPLETED",
    "issuesCount": 10
  }
]
~~~

### 2. Запустить новый прогон

`POST /api/runs`
Инициирует новый прогон: загружает активные цели и КР, прогоняет их через
`RuleEngine`, сохраняет найденные проблемы и фиксирует новый `kkd_run`.

**Пример ответа:**
`HTTP/1.1 201 Created` (пустое тело)

### 3. Получить список проблем (с пагинацией)

`GET /api/kkd/issues`
Возвращает список найденных проблем для конкретного прогона.

**Query Parameters:**

- `run_id` — ID прогона.
- `unit_id` (опционально) — фильтр по ID подразделения (с учетом дочерних
  подразделений и каскадирования целей).
- `rule` (опционально) — фильтр по коду правила (например, `GOAL_NO_OWNER`).
- `severity` (опционально) — фильтр по важности (`critical`, `major`, `minor`).
- `limit` (опционально) — количество записей (по умолчанию 20, макс 100).
- `offset` (опционально) — смещение (по умолчанию 0).

**Пример запроса:**
`GET /api/kkd/issues?run_id=1&severity=critical&limit=5`

**Пример ответа:**

~~~json
{
  "items": [
    {
      "id": 1,
      "ruleCode": "GOAL_NO_OWNER",
      "severity": "critical",
      "targetType": "GOAL",
      "targetId": 3,
      "message": "У цели отсутствует ответственный"
    }
  ],
  "limit": 5,
  "offset": 0,
  "total": 4
}
~~~

### 4. Получить сводную статистику (Summary)

`GET /api/kkd/summary`
Возвращает метрики, дельту и статистику по severity для конкретного
подразделения с учетом каскадирования целей.

**Query Parameters:**

- `run_id` (обязательный) — ID текущего прогона.
- `unit_id` (обязательный) — ID подразделения.

**Пример запроса:**
`GET /api/kkd/summary?run_id=2&unit_id=1`

**Пример ответа:**

### Формат ошибок

Все ошибки API возвращаются в едином формате:

~~~json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Run with id 999 not found"
  }
}
~~~

**Коды ошибок:**

- `404` — ресурс не найден (`NOT_FOUND`).
- `422` — ошибка валидации параметров (`VALIDATION_ERROR` или
  `INVALID_PARAMETER`).
- `500` — внутренняя ошибка сервера (`INTERNAL_ERROR`).

## 🧪 Как запустить тесты

Для интеграционных тестов используется **Testcontainers**, который

## 🔄 Работа с миграциями БД

В проекте используется Flyway. Поскольку Community-версия не поддерживает
автоматический откат (undo), для управления миграциями предусмотрены
bash-скрипты.

### Применение миграций (Накат)

Для создания схемы и загрузки стартовых данных выполните:

~~~bash
./scripts/migrate.sh
~~~

### Откат миграций

Для полного удаления схемы и данных (применение U1, U2, U3) выполните:

~~~bash
./scripts/rollback.sh
~~~

### Проверка жизненного цикла (Накат → Откат → Накат)

1. `./scripts/migrate.sh`
2. `./scripts/rollback.sh`
3. `./scripts/migrate.sh`

Если все три шага завершились успешно, значит схема БД и скрипты отката работают
корректно.

## 🏗 Архитектура решения

Проект построен по классической слоистой архитектуре: **Controller → Service →
Repository**.

### 1. Логика правил (Rule Engine)

Согласно ТЗ, логика правил полностью изолирована от слоя API и БД.

- **Где живет:** Пакет `rule`.
- **Как работает:** Интерфейс `KkdRule` реализуется 4 классами:
  `GoalNoOwnerRule` (нет ответственного), `KrWeightsSumRule` (сумма весов ≠
  100%), `KrNoTargetRule` (нет целевого значения), `KrStaleProgressRule` (факт
  не обновлялся > 45 дней). Они принимают объекты целей/КР в памяти и 
  возвращают список найденных проблем (`IssueProposal`).
- **Интеграция с БД:** Сервис `KkdRunService` загружает данные из БД через
  репозитории, передает их в `RuleEngine`, а затем сохраняет найденные проблемы
  в таблицу `kkd_issue`.

### 2. Расчет метрик и дельты

- **Метрики** (`clean_kr_share`, `avg_issues_per_goal`, `critical_goals_share`)
  рассчитываются в `KkdSummaryService` на основе агрегированных данных из
  `MetricsRepository`. Значения округляются до 1 знака после запятой.
- **Дельта** (new / persisting / resolved) рассчитывается на уровне SQL
  (`SummaryDeltaRepository`) с помощью CTE и оператора `IS NOT DISTINCT FROM`
  для корректного сравнения NULL-полей. Для первого прогона дельта равна `null`.
- **Каскадирование:** Скоуп метрик (список `goalIds`) собирается в
  `ScopeService` с помощью обхода в ширину (BFS) по иерархии подразделений и
  целей.

### 3. Особенности БД

- Для таблицы проблем (`kkd_issue`) используется паттерн **Exclusive Arc** (две
  колонки `goal_id` и `key_result_id` с CHECK-ограничением), чтобы избежать
  полиморфных связей.
- Поле `severity` в проблеме — это **снимок** важности на момент прогона, чтобы
  изменения в справочнике правил не искажали историю.
